# CLAUDE.md

Guidance for working on `linkthings-client-v3.0` specifically. This is a **fork of
`linkthings-client-v2`** (see the parent repo's `CLAUDE.md` and `linkthings-client-v2/CLAUDE.md` for
why that fork exists and its `Platform`/`Elevator`/`Clipboard` seam) that replaces the Bubble Tea TUI
with a **Wails v3 + Vue 3 + Tailwind desktop GUI**, adds a system tray with background-run behavior,
and replaces the HTTP OTP-provisioning flow with a direct SSH key-authorization flow. Module path:
`linkthings.io/client-v3`.

## What carried over from v2 unchanged

`config/`, `keymgmt/`, `logging/` (plus a small live-subscriber addition, see below), `paths/`,
`tunnel/` (all files, including the `Platform`/`TunDevice` seam and both OS implementations), and
`elevation.go`/`elevation_windows.go`/`elevation_linux.go`/`elevation_unsupported.go` — all copied
verbatim (only the import path changed from `linkthings.io/client-v2` to `linkthings.io/client-v3`).
None of this needed to change for a GUI. See `linkthings-client-v2/CLAUDE.md`'s "Architecture" section
for how the tunnel/routing/DNS code is organized — it applies here without modification.

## What's new or different

- **Dropped**: `ui/` (Bubble Tea) and `ui/clipboard*.go` — a Wails webview does
  `navigator.clipboard.writeText()` directly from Vue, so the Go clipboard abstraction is gone.
  Also dropped: `api/provisioning.go` and the `ServerConfig.ProvisionURL`/`OTPSharedSecret` fields.
- **`sshauth/sshauth.go`**: the new key-authorization flow. See
  [docs/CONFIG_REFERENCE.md](docs/CONFIG_REFERENCE.md#ssh-based-key-authorization-replaces-v2s-http-provisioning)
  for the exact behavior and its one documented limitation (root-only target account, no sudo relay).
- **`services/*.go`**: the Wails-bound Go structs the frontend calls (`ConnectionService`,
  `ProfileService`, `KeyService`, `AuthService`, `LogService`, `ElevationService`). Long-running work
  (Connect, Disconnect, the stats ticker) runs in a goroutine and reports back via Wails events
  (`conn-state`, `stats`, `log`) rather than blocking the calling method — the GUI equivalent of the
  TUI's `tea.Cmd`/`Msg` discipline. Exported methods on a registered service are **all** bound to the
  frontend automatically, so nothing service-internal (e.g. `ConnectionService`'s tray-menu-rebuild
  callback) can be an exported method — it's threaded through the constructor instead
  (`services/connection_service.go`), and `main.go` breaks the resulting circular dependency (tray
  menu needs the service, the service's callback needs the tray) with a forward-declared `var`.
- **`logging/logger.go`**: gained `Subscribe(func(Entry))` (fan-out to live listeners, used by
  `LogService` to stream to the frontend) and `Tail(n)` (best-effort parse of the existing plain-text
  log format, for the Logs screen's initial load). File writing behavior is unchanged.
- **`main.go`**: same elevation-gate-then-load-config-then-ensure-keys sequence as v2's `main.go`,
  but instead of `tea.NewProgram(...).Run()`, it builds a Wails `application.App`, a fixed-size
  `412×660` window (see the design handoff below for why), and a `SystemTray`. Closing the window
  hides it (`WindowClosing` hook + `Hide()` + `e.Cancel()`) instead of quitting;
  `DisableQuitOnLastWindowClosed` is set for both Windows and Linux so the app keeps running in the
  tray. The tray menu (Show/Connect/Disconnect/Exit) is rebuilt on every connection-state change.
- **`frontend/`**: Vue 3 + Vite + Tailwind v4 + TypeScript (`strict: true`, see
  `frontend/tsconfig.json`), using the `@config` directive to load the handoff's v3-style
  `tailwind.config.js` unchanged (that one file stays plain JS — it's loaded via a raw CSS file-path
  reference, not a JS import — see `frontend/src/style.css`). `@bindings` and `@` are Vite/TS path
  aliases (`frontend/vite.config.ts`) for the generated bindings directory and `frontend/src`.
  `frontend/bindings/` is generated by `wails3 generate bindings -ts ./...` (run from this directory,
  `-ts` for real `.ts` output instead of JSDoc'd JS) and is gitignored — regenerate it after changing
  any `services/*.go` method signature or adding a service. The three Wails events the frontend
  listens for (`conn-state`, `stats`, `log`) are registered in Go via `application.RegisterEvent[T]`
  (`services/connection_service.go`, `services/log_service.go`), so the generator emits a typed
  `CustomEvents` augmentation and `Events.On("conn-state", cb)` is fully typed on the frontend with
  no hand-maintained event types — register any new event the same way. `frontend/src/composables/*.ts`
  wrap the generated bindings + `@wailsio/runtime`'s `Events.On` per concern (connection, profiles,
  key, auth, logs, elevation); components under `frontend/src/components/` are one per screen
  (`ConnectView`, `ProfilesView`, `SshKeyView`, `LogsView`) plus shared chrome (`TopBar`, `TabBar`,
  `StatusStrip`, `ProfilePicker`), all on `<script setup lang="ts">`. `npm run type-check` (`vue-tsc
  --noEmit`) and `npm run lint` (ESLint + typescript-eslint + eslint-plugin-vue, `frontend/eslint.config.js`)
  are separate from `npm run build`, which runs the type-check first and then `vite build`.

## The design source of truth

`design_handoff_linkthings_client/` (README.md, TAILWIND_MAPPING.md, tailwind.config.js,
linkthings-ui.html) is the pixel-fidelity spec for the "Nocturne" UI — screens, bindings table
(illustrative, not literal — see `docs/CONFIG_REFERENCE.md` and the services above for the actual
binding surface), state shape, and layout invariants (fixed 514px body for Connect/SSH-key/Logs, the
Profiles list's own internal scroll, the profile-picker overlay never pushing content). Where a
screen's exact pixel values matter, open `linkthings-ui.html` in a browser and inspect it rather than
guessing from the markdown.

## Known operational caveat: elevated GUI vs. the X11/Wayland display and D-Bus session on Linux

A pkexec-elevated process on Linux commonly fails to reach the X11/Wayland display at all
("Failed to open display" from GTK), and separately fails to reach the desktop session's D-Bus
(root has no `/run/user/0/bus` of its own), because the elevated (root) process doesn't
automatically inherit the calling user's display/auth cookie or session bus address — this is
generic Linux desktop friction with running *any* GUI app as root via `pkexec`/`sudo`, not specific
to this app's code. It didn't matter for v2 (a terminal-only TUI has neither a display nor a tray
to open), but it's a real practical consequence of this version's "whole app, including the window
and tray, runs elevated for its entire lifetime" choice (see the parent repo's plan history — this
was a deliberate decision, not an oversight) once there's an actual window and tray to show.

Direction (a) below is implemented: `elevation_linux.go`'s `RelaunchElevated` explicitly forwards
`DISPLAY`/`XAUTHORITY`/`WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR`/`DBUS_SESSION_BUS_ADDRESS`
(`sessionEnvVars`) to pkexec rather than relying on its default environment handling — the
D-Bus var was the last one added, after the tray icon was found to silently never register under
elevation (Wails' Linux systray logs `"systray error: failed to connect to DBus"` and returns
rather than failing loudly, so the window still works and the missing tray icon is easy to miss).
If some other desktop-session-scoped resource turns out to need the same treatment, add it to
`sessionEnvVars` rather than reaching for direction (b): revisiting the "whole app elevated" model
in favor of a small privileged helper for just the tunnel/adapter/route operations, leaving the
window+tray unprivileged (the alternative that was explicitly declined when this was decided —
reconsider only if passthrough env vars prove insufficient in practice, not preemptively).

## Known simplification vs. the design handoff

The handoff's SSH-key screen assumes a persistent "authorized on N/total profiles" signal driven by
the old HTTP provisioning flow's responses. That flow is gone and there's no replacement source of
truth for "is this profile authorized" (the SSH-auth flow only reports success/failure at the moment
you run it). The "Authorized on" card is implemented as session-scoped, client-side state instead
(profiles this machine's key has been sent to *during the current app run*) — flagged in the frontend
with a comment rather than presented as durable, server-verified status.

## Commands

```bash
cd linkthings-client-v3.0

# Go: same cross-platform build matrix as v2
go build ./...
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o dist/linkthings.win.amd64.exe .
go vet ./...
gofmt -l .

# Frontend (from linkthings-client-v3.0/frontend)
npm install
npm run type-check                  # vue-tsc --noEmit
npm run lint                        # eslint .
npm run build                       # type-check, then writes frontend/dist (embedded by main.go's go:embed)

# Regenerate Go->TS bindings after changing services/*.go (from linkthings-client-v3.0)
wails3 generate bindings -ts ./...

# Full app dev loop — needs libgtk-4-dev + libwebkitgtk-6.0-dev on Linux (Ubuntu 24.04+/Debian 13+;
# see https://v3.wails.io/quick-start/installation for older distros' GTK3 fallback tag)
wails3 dev
```

There is still no `*_test.go` suite. Verification is: `go vet`/`gofmt`/`go build` for both
`GOOS=linux` and `GOOS=windows`, `npm run build` for the frontend, and — since this dev machine has a
real (non-stub) Linux tunnel implementation — actually running the app to exercise Connect/Disconnect
end-to-end. Running it requires the app's own admin/root elevation gate to succeed (UAC on Windows,
`pkexec` on Linux), which needs an interactive prompt a non-interactive shell can't satisfy — expect
that, don't try to bypass it.
